On Azure, the managed model API lives in **Microsoft Foundry**, which was called Azure AI Foundry until Microsoft renamed it at Ignite in November 2025 (and Azure AI Studio before that). Inside it, "Foundry Models" covers the models Azure sells directly, including the Azure OpenAI models, and it also lists models from other providers. Older docs, SDKs and forum posts still say "Azure OpenAI Service" or "Azure AI Foundry". They mostly point to the same things.

The part that trips teams up is not the API call. It is the **deployment**: the object that decides how your requests are billed, where they run, and whether capacity is held for you.

## Deployment types

You create a deployment of a model, and you choose a type. There are two choices to make: the billing and capacity behaviour, and the geographic scope.

<DeploymentGrid client:visible />

Batch is offered at Global and Data Zone scope, with no regional option. A "Developer" tier also exists, but only for evaluating fine-tuned models. It has no SLA and its deployments are deleted after 24 hours, so it is not for production. Standard deployments can also use Flex (cheaper, slower) or Priority (faster, pay as you go) processing for individual requests, where a model supports them.

## Quota is not capacity

This is the most important idea in the lesson. **Quota** is a policy limit: the most PTUs you may deploy in a subscription, region and deployment type. It is free to hold. **Capacity** is the actual hardware available when you try to create the deployment.

Microsoft's docs are direct about it: having PTU quota does not guarantee capacity is available. If the region cannot supply the PTUs you ask for, the deployment fails. So work in this order:

## When to choose provisioned

Provisioned is billed per PTU per hour whether or not you send traffic. It fits when traffic is predictable, users need steady latency, and volume is high enough that per-token billing costs more than the hourly commitment. Standard fits everything else. Work out the break-even with your own token volumes and the current prices, since this lesson does not quote any.

PTUs are not tied to one model. The same quota can back any supported model, but the same PTU count buys different throughput on different models. A cache hit does not consume PTU capacity, so good prompt caching reduces how many PTUs you need.

## Spillover

If a provisioned deployment is full and returns a `429`, **spillover** can send the overflow to a matching standard deployment in the same resource. Azure OpenAI models support it. Models from some other providers did not, as of the docs checked on 26 October 2026. You pay standard rates for what spills over and accept standard latency for it.

<Deep title="Sizing a PTU deployment">
Microsoft's sizing method uses three inputs: requests per minute, average input and output tokens per request, and your cache hit rate. Output tokens count for more than input tokens, using a per-model ratio. The result is a normalised tokens-per-minute figure, divided by a per-model "input tokens per minute per PTU" value. Each model also has a minimum PTU count for a deployment. Use the capacity calculator in the portal and the per-model table in the docs, because the numbers change with each model.

## Content safety and search, at a high level

Foundry applies **guardrails** (previously called content filters) to prompts and responses, with configurable thresholds. For retrieval, the Azure building block is **Azure AI Search**, which holds your documents and vectors and is queried to ground a model's answer. Both are separate resources from the model deployment, with their own cost and failure modes, and the retrieval quality lessons apply unchanged: see [chunking and retrieval quality](../../rag-agents/chunking-and-retrieval-quality/).

## Azure Machine Learning versus Foundry

Use **Foundry** when you want to call hosted models, build agents and evaluate them. Use **Azure Machine Learning** when you train or host your own models on compute you control, or run classical ML pipelines. Boundaries overlap, and Microsoft keeps moving features between them, so check the current docs for the one you need.

## What to take forward

- Pick the type (Standard, Provisioned, Batch) and the scope (Global, Data Zone, Regional) separately.
- Quota is permission. Capacity is hardware. You can have the first without the second.
- Choose provisioned only for steady, latency-sensitive load, and test whether the deployment can be created.
- Plan spillover and a fallback model for when a deployment returns `429`. See [Quotas, capacity and regions](../quotas-capacity-and-regions/).
