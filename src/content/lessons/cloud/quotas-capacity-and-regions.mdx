Most AI projects hit their first cloud wall in the same place: the code works, the model is chosen, and the request for GPUs or throughput is refused, throttled or stuck. Capacity is a planning topic, not an afterthought.

## Why capacity is scarce

Accelerators are expensive, built in limited numbers, and a large model needs many of them linked by fast networking in the same place. A cloud cannot simply spin up more. Demand is also uneven across regions and moves through the day. So every cloud rations access in two ways: **quota**, which is a permission limit, and **capacity**, which is real hardware. You can have the first without the second.

## Three capacity models

| Model | What it is | Trade-off |
|---|---|---|
| On-demand, shared | Pay as you use, capacity shared with other customers | Flexible, but you can be throttled or refused at peak |
| Provisioned or reserved | You pay to hold a fixed slice, whether used or not | Predictable latency and throughput, but you pay for idle time |
| Reservations, blocks, Flex-start and Spot | You book capacity for a set period, queue for it, or use spare capacity that can be taken back | Good for training and batch, with scheduling effort |

### Managed model APIs

On Bedrock, Azure and Gemini, the on-demand option is per-token billing with rate limits. The provisioned options are Bedrock Provisioned Throughput (and service tiers), Azure PTUs, and Gemini Provisioned Throughput. On Azure, PTU quota does not guarantee capacity, and a deployment can fail if the region lacks it. Read [Microsoft Foundry and Azure OpenAI](../microsoft-foundry-and-azure-openai/) for that case.

### GPU virtual machines

- **Azure:** every subscription starts with zero vCPU quota for GPU VM series per region. You must request an increase before you can create an ND or NC machine. Microsoft says net new capacity for the NC A100 v4 series is only going to NCads H100 v5, so check which sizes are still being sold.
- **Google Cloud:** A3 Ultra (H200) and A4 (B200) cannot be provisioned as ordinary on-demand VMs. They need a capacity reservation, Spot, or Flex-start. Older types such as A3 Mega and A2 may be easier to obtain, but check per zone.
- **AWS:** **EC2 Capacity Blocks for ML** let you reserve GPU instances for a defined time window. P6-B200 instances were launched through Capacity Blocks. P5 and P6 families are also available through other purchase options, so check the instance page.

Treat all of this as of October 2026. Instance names, availability and the rules for getting them change often.

## Regions and residency

Capacity is regional, and so is quota. **Cross-region inference** (AWS inference profiles, Azure Global deployments, Google global endpoints) can route a request to wherever there is room, so throttling falls. The cost is **residency**: your prompts may be processed outside your home region or zone.

## Planning checklist

- List the exact models and GPU types you need, and check each exists in your target regions.
- Estimate peak tokens per minute and requests per minute.
- File quota requests early, since approvals on some clouds take days.
- Verify capacity, not only quota, by creating the deployment or reservation in a test.
- Decide the residency scope, and what it costs in capacity.
- Pick a capacity model per workload: provisioned for interactive baseline, batch for bulk, blocks or Spot for training.
- Build retry, queueing and a tested fallback before launch.
- Re-check the cloud docs every quarter, since the rules and names keep changing.
