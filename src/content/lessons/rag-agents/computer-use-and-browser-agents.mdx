Most software has no API, or has one that does not expose the thing you need. A computer-use agent gets around that by using the software the way a person does: it looks at the screen, moves the pointer, clicks and types. That makes it useful for old internal tools, for web forms and for testing. It also gives it the one property that makes it dangerous: it acts with whatever the logged-in user can do, while reading pages written by strangers. [LLM application security](../../evals/llm-security/) describes that combination in general. This lesson is about what it looks like with a screen.

This is the [agent loop](../agents-and-tool-use/) with a screen as the tool. The model never touches the machine. Every provider's documentation describes the same split: the model proposes actions, and your application executes them in an environment you provide and sends back the result. As of 1 November 2026:

| Provider | What the docs describe | What they tell you about safety |
|---|---|---|
| Anthropic | A computer-use tool that runs client-side: you execute each action and return screenshots. The page says it is stable on the Claude API and Google Cloud and in beta on Amazon Bedrock and Microsoft Foundry. For web-only tasks it points to a separate browser-use tool. | Use a dedicated VM or container with minimal privileges, keep sensitive data and logins away, limit internet access to an allow-list, ask a person to confirm consequential decisions. |
| OpenAI | A `computer` tool in the Responses API: the model returns a list of actions, you run them and return a screenshot. The page also describes an alternative where the model writes Playwright or similar code. | Isolated browser or VM, a fresh profile, an allow-list of sites; page text "cannot grant permission or override the user's instructions"; confirm purchases and data sending; check the real outcome, not the model's final answer. |
| Google (Gemini API) | A computer-use tool: the model returns function calls with an `intent`, and coordinates on a 0 to 999 scale that you convert to pixels. | Responses can carry a `safety_decision` such as `require_confirmation`; sandbox, allow-lists and logging; an opt-in detector for hidden instructions in screenshots; "may contain errors and security vulnerabilities". |
| Microsoft (Foundry) | A computer-use tool backed by the `computer-use-preview` model, with registration and eligibility checks for access; items marked preview are not recommended for production. | Use VMs with no sensitive data; built-in checks for malicious instructions, irrelevant domains and sensitive domains; do not run an action with pending safety checks without user approval. |
| AWS | Amazon Nova Act, for browser workflows through an SDK, and Bedrock AgentCore Browser, a managed isolated browser with live view, session recording and a default 15-minute session timeout. | The Nova Act service card recommends a domain allow-list, registering only the tools a workflow needs, and human oversight for high-risk steps. It says it "cannot guarantee" that all prompt injections are deflected. |

Screens add small engineering costs that APIs do not have. Coordinates must be scaled back if you shrink the screenshot. With the 0 to 999 convention, a model answer of x = 500 on a 1,280-pixel-wide screen means 500 / 1000 × 1280 = 640 pixels. Anthropic's page suggests 1,280 × 800 or 1,366 × 768 for web apps and says long loops accumulate roughly 1,000 to 1,800 tokens per screenshot. As a worked example, forty screenshots are 40,000 to 72,000 tokens of images alone, before the history is counted again on each turn. No page I read gave a time per step, so measure your own.

## What the model sees: pixels or an outline

There are two ways to show a page to a model. A **screenshot** works on anything, including canvases, remote desktops and apps with no markup, but the model must pick exact positions. An **accessibility tree** is a text outline of the page's roles and names, which Playwright calls an ARIA snapshot, for example `heading "title"` or `button "Add to basket"`. Microsoft's Playwright MCP server gives the model these snapshots instead of images and says no vision model is needed; screenshots are an opt-in extra. The SeeAct paper (2024) found that grounding, turning a plan into the right element, is the main difficulty, that visual-only grounding with set-of-mark prompting was ineffective, and that combining page structure with the image worked best. That was with GPT-4V; treat it as a reason to test both on your own pages, not as a ranking.

Whichever you choose, **the attacker's words arrive through both.** Pale text in a review is nearly invisible to a person and is plain text in the outline. The lab below shows both views.

## Where they fail

Public benchmarks give the clearest picture of reliability. When first published, OSWorld (369 open-ended computer tasks) reported 72.36% success for humans and 12.24% for the best model, and WebArena reported 78.24% for humans and 14.41% for a GPT-4-based agent. These are early results and agents have improved since: the OSWorld page notes a verified version dated 28 July 2025 and an OSWorld 2.0 as of 26 June 2026, but its leaderboard would not load for me, so I cannot quote a current score. Read the live leaderboard, and note which model, scaffold and number of attempts it uses.

The vendors' own pages describe the failures. Anthropic says the model "sometimes acts as if its actions succeeded without explicitly checking", and that dropdowns, scrollbars and small targets cause misclicks. Google says unexpected pop-ups and layout changes can confuse the model. OpenAI notes that clicks can miss and that session state lives in your environment, not in the API conversation. The Nova Act card lists a limit of 100 sequential steps and 30-minute browser sessions as of its December 2025 date.

Long tasks compound small error rates. If each step succeeds independently with probability p, a task of n steps succeeds with probability p to the power n. These are example numbers, and real errors are not independent, but the shape is the point:

| Per-step success | 5 steps | 10 steps | 20 steps | 50 steps |
|---|---|---|---|---|
| 95% | 77% | 60% | 36% | 8% |
| 99% | 95% | 90% | 82% | 61% |

Shorter tasks, checkpoints after each stage, and a person to take over at login screens and CAPTCHAs (AgentCore Browser and Nova Act describe human takeover; Gemini's docs suggest adding a hand-off function) are how you work around it.

## Hidden instructions on the page

A language model reads instructions and page text in one stream. A web page is written by whoever controls it, or by anyone who can post a review, a comment or an advert. Anthropic's computer-use page says the model sometimes follows commands found in content even when they conflict with the user's instructions, and that it runs classifiers on screenshots to flag likely injections.

Anthropic's November 2025 research on its Chrome agent gives a sense of the size of the problem. Against an internal adaptive attacker that tried 100 attempts per environment, the attack success rate for Opus 4.5 fell from 8.0% with the model alone to 1.4% with the improved safeguards, and the lowest of the four models tested, but the post says plainly that a 1% rate "still represents meaningful risk" and that no browser agent is immune. That is one vendor's own test on its own attacker. It shows that defences in the model and a classifier help, and that none of them is a guarantee.

The lab shows why you build controls that do not depend on the model noticing. A pretend agent is buying a book. A review hides an instruction. We assume the model is fooled, and you switch defences on and off.

Read the matrix at the bottom. The allow-list stops the attack that sends data to another site and does nothing against one that uses the shop's own review box. The page filter is scripted to catch the plain wording and miss the disguised one, to stand for what probabilistic detectors do: they reduce attacks, and sometimes miss. The two controls that held in both cases are the ones that remove what the attacker needs:

- **A clean sandbox** means there is nothing to steal: no saved address, no logged-in session. Its cost is that tasks which need a login end with a hand-off to a person.
- **A confirmation gate** means data cannot leave, and money cannot be spent, without a person seeing the action. Its cost is prompts, and the lab assumes the person reads each one. Real people approve what they are asked so often that the prompt becomes a habit. Keep prompts for irreversible actions only: purchases, sending, publishing, deleting, changing permissions, accepting terms. Gemini's built-in categories (financial transactions, communications, account creation, legal agreements and others) are a reasonable starting list.

## A safe-enough design

1. **Isolate.** A disposable VM, container or managed browser session per task, a fresh profile, no personal cookies. Destroy it afterwards.
2. **Give it the least.** A separate account with narrow permissions, not yours. No saved payment methods. Secrets never in the page text or the prompt.
3. **Restrict the network.** Allow-list the domains the task needs, and block local files and uploads unless needed. Nova Act's card says file upload and `file://` access are blocked by default in its SDK.
4. **Gate irreversible actions** on a person's approval, showing the exact action and data, not a summary.
5. **Cap the run.** Step, time and cost limits, and a way for a person to stop it.
6. **Record everything.** Screenshots, actions and approvals. AgentCore Browser offers session recording and live view, and Gemini's docs say to log everything.
7. **Judge the end state.** Check the order, record or file that should exist, not the agent's closing message.

## When an API or a tool is better

A screen agent is the last resort, not the first. In order of preference:

1. **A real API**, called by ordinary code. It is faster, cheaper, structured, auditable and can be permission-scoped.
2. **An MCP or function tool** that wraps the API for the model. See [MCP in depth](../mcp-in-depth/) and [Designing tools for agents](../designing-tools-for-agents/).
3. **A scripted browser flow** (for example a Playwright script) when the path is stable. A model can help write it once, and then it runs the same way each time at no model cost.
4. **A browser agent** when pages vary or no script is practical, using the accessibility outline where the page allows.
5. **A screenshot desktop agent** for software with no web or API surface at all.

Anthropic's own page recommends its browser-use tool for web-only tasks, which is this ladder in miniature. Use a screen agent where the alternative is a person doing the same clicks, the task is bounded and checkable, and a mistake is cheap to undo.

## What to remember

- A screen agent is the agent loop with screenshots in and mouse and keyboard actions out. Your harness, not the model, performs every action.
- Screenshots work everywhere and need precise positions; an accessibility outline is smaller and exact but covers less. Both carry any hidden text on the page.
- Early benchmarks showed large gaps to humans and agents have improved, but long tasks still compound small error rates and need checkpoints and hand-offs.
- Web pages are untrusted input. Model-side training and classifiers lower the risk and no vendor claims they remove it.
- Controls that do not depend on the model: a clean sandbox, no credentials, an allow-list, confirmation for irreversible actions, and caps. Each has a cost to plan for.
- Prefer an API, then a tool, then a script, before a screen agent.
