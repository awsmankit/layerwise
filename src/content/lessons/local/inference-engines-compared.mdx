An inference engine is the program that loads a model and turns prompts into tokens. The model is the same idea everywhere, but the engines differ a lot in what they are built for. Some are made for one person on a laptop. Others are made to serve hundreds of people at once on a rack of GPUs. Picking the wrong kind is the most common local-inference mistake.

<Callout title="Engines change fast" kind="note">
The descriptions below are general and reflect the projects as understood in October 2026. Supported hardware, model families and quantization formats change with almost every release. Check each project's own documentation before you commit.
</Callout>

## Laptop runner versus production server

A laptop runner is optimised for **one user, one request at a time, on whatever hardware you have**. It starts quickly, runs on modest memory and works on CPUs and Apple chips.

A production server is optimised for **throughput across many concurrent users on GPUs**. Three techniques matter most.

- **Continuous batching.** Instead of waiting for a whole batch to finish, the server adds new requests and removes finished ones at every step. The GPU stays busy, and one read of the weights serves many users.
- **PagedAttention.** The KV cache is stored in small blocks rather than one big reserved region per request, which wastes far less memory, so more requests fit (see [the KV cache lesson](../../serving/kv-cache-and-memory/) and the PagedAttention paper).
- **Prefix caching.** Requests that share a starting prompt, such as the same system prompt, reuse the cache already computed for it.

Many engines now have some version of each technique, so check what a given one supports rather than assuming.

## The comparison

| Engine | Target hardware | Strengths | Trade-offs | Typical user |
| --- | --- | --- | --- | --- |
| llama.cpp | CPU, Apple silicon, and many GPUs | Runs almost anywhere, GGUF quantization, small footprint, built-in HTTP server | Not designed for large multi-user GPU serving | Hobbyists, developers, edge and embedded use |
| Ollama | Mac, Windows, Linux | Very easy: one command to download and run, local API | Less tuning control, and aimed at a single machine | Beginners, personal tools, prototypes |
| vLLM | Mainly GPU servers (NVIDIA is the best supported, other vendors vary by version) | PagedAttention, continuous batching, prefix caching, broad model support | Heavier to set up, wants a real GPU | Teams serving many users on one or a few GPUs |
| TGI (Hugging Face) | GPU servers | Still runs existing deployments | In maintenance mode since December 2025 and archived in March 2026; Hugging Face recommends vLLM or SGLang for new work | Only teams with existing TGI deployments, planning a migration |
| TensorRT-LLM | NVIDIA GPUs only | Highly optimised kernels, can give top performance on NVIDIA | Model compile and build steps, less flexible, vendor lock-in | NVIDIA fleets where the last bit of speed pays |
| SGLang | GPU servers | Efficient serving, strong prefix reuse, good for structured and multi-step programs | Younger ecosystem, check model support | Teams with agent-style or heavily shared-prefix traffic |

"Strengths" here are what each project positions itself on. Real speed depends on the model, hardware, settings and version, so benchmark on your own workload.

## OpenAI-compatible APIs: the common plug

Most of these engines can expose an HTTP API that follows the shape of the OpenAI chat API. That is the practical integration point: your application talks to a base URL, and you can swap an engine or a cloud provider by changing that URL and the model name. The usual details (which endpoints, which parameters, tool calling, structured output) vary by engine, so test the features you rely on. It also makes it easy to start on a laptop with Ollama and later move to vLLM on a server.

## Quantization formats

Support differs by engine, and changes often. As a rough guide (verify in each project's docs):

- **GGUF** is the native format of llama.cpp and the tools built on it.
- GPU server engines tend to favour formats such as **GPTQ**, **AWQ**, FP8 and other hardware-specific options, plus unquantized 16-bit weights.
- Some engines can also load GGUF, often with caveats.

See [Quantization](../../serving/quantization/) for how these methods differ.

## A decision guide

<EngineTree client:visible />

<Deep title="Why Ollama is not a production server">
Ollama is built around the llama.cpp family of engines and a one-command experience. It can serve an API and handle a few concurrent requests, but it is designed for a single machine and personal use. When you need to serve dozens of users with predictable latency, an engine built around continuous batching and paged cache management, run behind a load balancer, is normally a better fit. Measure rather than assume: a modest load on a well-sized machine may be fine.
</Deep>

## What to take forward

- Match the engine to the job: laptop runners for one person, batching servers for many users.
- Continuous batching, PagedAttention and prefix caching are why servers get far more out of a GPU.
- An OpenAI-compatible API lets you change engines without rewriting your app.
- Benchmark on your own model, hardware and prompts, using the version you will actually run.
