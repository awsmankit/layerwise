A language model is, underneath, a very large pile of multiplications and additions. Running one means doing billions of them for every word. This lesson explains the chip that does that work well, and the one idea that explains most of what you will later read about AI hardware: sometimes the chip waits for arithmetic, and sometimes it waits for data.

## CPU versus GPU

A **CPU** has a handful of powerful cores (a laptop has 8 to 16, a server maybe 64 to 128). Each core is clever. It handles branching, unpredictable code and many different kinds of tasks quickly, one after another. Think of a few expert chefs who can cook anything.

A **GPU** (graphics processing unit) has thousands of much simpler arithmetic units. Each one is slow and not clever, but they all work at the same time on different pieces of the same job. Think of a huge kitchen line where every cook does one simple step, all at once. GPUs were built to colour millions of screen pixels at the same time. It turned out that the same trick suits neural networks.

## Why matrix multiplication fits

A neural network layer is mostly a **matrix multiplication**: a big grid of weights multiplied by a grid of numbers coming in. Each cell of the answer is a separate sum of products, and none of those sums depends on the others. That is exactly the kind of work you can hand to thousands of workers at once.

Modern datacenter GPUs add special units called **tensor cores**. A normal arithmetic unit multiplies two numbers. A tensor core multiplies and adds a whole small block of numbers in one step, usually in a low-precision format such as 16-bit or 8-bit. Most of the headline speed in a GPU's datasheet comes from these.

## The other chip names

| Chip | What it is | In one sentence |
|---|---|---|
| GPU | NVIDIA, AMD and others | General parallel hardware with tensor cores. Runs almost any model. |
| TPU | Google's accelerator | Built around large matrix units. Used on Google Cloud. |
| Trainium, Inferentia | AWS accelerators | Amazon's own chips for training and inference. |
| NPU | Neural processing unit | A small accelerator in a phone or laptop, for on-device models. |

TPUs, Trainium and Inferentia need different software from the NVIDIA world (for example, AWS uses its Neuron SDK instead of CUDA). The ideas in this track apply to all of them, though the vocabulary changes.

## Compute-bound and memory-bound

Picture a restaurant kitchen. If customers order dishes that take a lot of chopping and cooking, the cooks are the limit. Hire more cooks and you serve more. That is **compute-bound**: the work is limited by arithmetic speed.

Now picture a kitchen where each dish needs one pinch of salt, but the pantry is down a long corridor and only one person can carry things at a time. The cooks stand around waiting. More cooks would not help. A wider corridor would. That is **memory-bound**: the work is limited by how fast data moves from memory to the arithmetic units.

The same chip can be either, depending on how much arithmetic you do per byte you fetch.

## Why generating text is memory-bound

Reading your prompt is compute-bound. The model processes all your words in one large batch of arithmetic, so the tensor cores stay busy. This is called **prefill**.

Writing the reply is different. The model produces one token, then needs the result to produce the next. For each token it must read all of its weights from memory (an 8-billion-parameter model in 16-bit form is about 16 GB), do a comparatively small amount of arithmetic with them, and then do it all again. The arithmetic units mostly wait. This phase is called **decode**, and its speed is set by memory bandwidth, not by the headline compute number.

That is why a GPU with faster memory can generate text faster even if its arithmetic speed is the same. It is also why serving many users at once helps: one read of the weights can serve many requests in the same step.

<Callout title="The idea to keep">
Prefill is limited by arithmetic. Decode is limited by memory bandwidth. Almost every spec, trade-off and cost question in this track comes back to which of the two you are in.
</Callout>

<Deep title="Arithmetic intensity, the precise version">

The ratio of arithmetic operations to bytes moved is called **arithmetic intensity**. Every GPU has a break-even intensity: its peak operations per second divided by its memory bandwidth. Work below that intensity is memory-bound, work above it is compute-bound. Decode for one user does roughly two operations per weight read (one multiply, one add), and a 16-bit weight is two bytes, so its intensity is about one operation per byte. Datacenter GPUs break even at something like a few hundred operations per byte, so single-user decode sits far into memory-bound territory. Batching raises intensity because each weight read is reused across the batch, until you cross over and become compute-bound or run out of memory for the KV cache. The [next lesson](../reading-a-gpu-spec-sheet/) turns this into a formula you can use.

</Deep>

<Disclosure client:visible title="Why not just use a CPU?">

You can, and for small models it works. Optimised CPU runtimes such as llama.cpp run quantized models on laptops. But a CPU has far less memory bandwidth and far fewer arithmetic units than a datacenter GPU, so large models and many simultaneous users quickly become slow. See [Edge versus cloud inference](../../edge/edge-vs-cloud-inference/) for the other end of that trade-off.

</Disclosure>

## What to take forward

- A GPU does thousands of simple operations at once, which suits matrix multiplication.
- Tensor cores are the fast arithmetic units. HBM is the fast memory.
- Compute-bound means waiting for arithmetic. Memory-bound means waiting for data.
- Reading a prompt is compute-bound. Generating a reply is memory-bound.
- Other accelerators (TPU, Trainium, Inferentia, NPU) follow the same logic with different software.
