Most readers will fine-tune rather than pretrain, but the same machinery runs both, and knowing it explains the costs and the failure stories. This lesson covers what is in a training cluster, how sharding makes a big model fit, and how teams survive hardware that fails every few hours. For where training sits in the larger picture, see [The training pipeline](../../foundations/training-pipeline/).

## What a training cluster is

Shared storage is usually a parallel file system or an object store. The scheduler decides which job gets which nodes, queues work and restarts jobs.

## The memory budget of training

Inference needs weights and KV cache. Training needs much more. With the common mixed-precision recipe and the Adam optimizer, the ZeRO paper counts about 16 bytes per parameter before activations:

| Item | Bytes per parameter |
|---|---|
| Weights (16-bit) | 2 |
| Gradients (16-bit) | 2 |
| Master copy of weights (32-bit) | 4 |
| Adam momentum (32-bit) | 4 |
| Adam variance (32-bit) | 4 |
| Total | 16 |

A 7-billion-parameter model therefore needs about 112 GB for this state, more than one 80 GB GPU. A 70B model needs about 1.1 TB. On top comes **activation** memory, the intermediate results kept for the backward pass. It grows with batch size and sequence length. **Activation checkpointing** (recomputation) saves memory by recomputing activations instead of storing them, in exchange for extra compute.

## Sharding: ZeRO and FSDP

Plain data parallelism copies all 16 bytes per parameter to every GPU, which wastes memory. **ZeRO** shards it in three stages: first the optimizer state, then the gradients, then the parameters themselves, which stage 3 gathers layer by layer just in time.

<ZeroStages client:visible />

PyTorch's **FSDP** (fully sharded data parallel) does the equivalent of stage 3 by default. With N GPUs and full sharding, the per-GPU share of that 16-byte state falls to roughly 16 divided by N bytes per parameter, so the 70B model on 64 GPUs needs about 17.5 GB of state per GPU, leaving room for activations. The price is more communication, since parameters are gathered before use and gradients are scattered after, but it overlaps with compute and runs well over fast fabric.

<Deep title="Combining sharding with tensor and pipeline parallelism">

Very large runs mix methods. Tensor parallelism inside a node, pipeline across nodes and data parallelism with sharded state on the outside is the pattern described in the Megatron 3D parallelism paper. Sharding helps when the model's state does not fit, while tensor parallelism helps when the per-layer compute or activations are too big for one GPU. The Llama 3 paper describes a 405B-parameter run on up to 16K H100 GPUs using this kind of multi-dimensional parallelism, and reports a model FLOPs utilisation of roughly 38 to 43 percent in its configurations. That is a useful reality check: even expert teams use well under half of the theoretical peak, because communication, pipeline bubbles and memory-bound operations take their share.

</Deep>

## Failure is routine

Synchronous training means one bad GPU can stall every other GPU, so a single fault can stop the whole job. Meta's Llama 3 report gives real numbers: in a 54-day snapshot of pre-training on a cluster of 16K GPUs there were 466 job interruptions, 47 planned (maintenance) and 419 unexpected. About 78 percent of the unexpected ones were attributed to confirmed or suspected hardware problems, GPUs being the largest single category. That is roughly one unexpected interruption every three hours. Meta reached over 90 percent effective training time only through automation, fast checkpointing and diagnostic tools, and needed manual intervention just three times in that period.

So every serious run needs:

- **Frequent, fast checkpoints.** On average you lose half a checkpoint interval per failure. Checkpoints for full resume are about as large as the training state (around 16 bytes per parameter), so writing them well, in parallel and asynchronously, matters.
- **Automatic detection and replacement** of bad nodes, plus spare capacity to swap in.
- **Diagnostics for hangs**, such as communication-library tracing, since a stuck collective looks like silence.

## Managed options

As of October 2026, and with details that change, check each doc:

- **AWS.** SageMaker HyperPod provisions resilient GPU or Trainium clusters orchestrated with Slurm or Amazon EKS. Its resiliency features monitor instances and replace faulty hardware, and EKS-based clusters support job auto-resume for Kubeflow PyTorch training. P5 and P6 instances are reserved with Capacity Blocks.
- **Azure.** ND-series VMs (ND H100 v5, ND H200 v5, ND GB200 v6) with InfiniBand are the building blocks. Teams run them under Slurm or AKS. Check the current Azure documentation for the cluster management options.
- **Google Cloud.** A3, A4 and A4X machines and TPUs are used through GKE or Slurm-based setups. Check the current documentation for the cluster and scheduler offerings, since names change.

## Data pipelines and cost levers

Keep data tokenized and stored in large sequential files so reads are fast, and shuffle and shard deterministically so a restart can resume from the same position. The main cost levers are:

- **Reservations** for the main run, such as Capacity Blocks or committed capacity, so the cluster is there when you start.
- **Spot capacity** for fault-tolerant work such as fine-tuning, evaluation or smaller experiments, with frequent checkpoints so an interruption costs minutes, not hours.
- **Efficiency.** Higher GPU utilisation through better data loading, overlap of communication and compute, and appropriate precision (BF16 or FP8) lowers the bill more than shopping for a cheaper instance.
- **Right-sizing.** Fine-tuning with LoRA or a similar method needs far less memory than full training. See [Prompting vs RAG vs fine-tuning](../../llm/prompting-vs-rag-vs-fine-tuning/) before you commit to training at all.

An idle reserved cluster bills the same as a busy one. Have the data, the code and a tested restart path ready before the reservation starts, and run a short trial on a small scale first.

## What to take forward

- Training state is about 16 bytes per parameter before activations, which is why one GPU is not enough.
- FSDP and ZeRO shard that state. Tensor and pipeline parallelism handle what sharding cannot.
- At this scale, interruptions are daily events. Plan checkpoints and automated recovery from the start.
- Reserve for the main run, use Spot with checkpoints for the rest, and measure utilisation.
