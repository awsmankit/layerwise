All three big clouds rent you GPUs by the hour, but they name and package them differently, and getting access is often harder than choosing. This lesson maps the families, says what each is for, and explains the quota and reservation rules that catch teams out. Everything here is as of October 2026. Instance lists change every few months, so use the linked pages for the final word.

## The families, side by side

| | AWS | Azure | Google Cloud |
|---|---|---|---|
| Newest large-scale training | P6e-GB200, P6-B300, P6-B200 | ND GB200 v6 (4 Blackwell GPUs per VM, 18 VMs form a 72-GPU rack) | A4X (GB200), A4X Max (GB300, bare metal), A4 (8x B200) |
| Hopper generation (H100, H200) | P5 (H100), P5e and P5en (H200) | ND H100 v5, ND H200 v5 | A3 Mega, High and Edge (H100), A3 Ultra (H200) |
| Older training | P4 (A100) | ND A100 v4 (8x A100 40 GB) | A2 (A100) |
| Inference and fine-tuning, NVIDIA | G6 (L4), G6e (L40S), G5 (A10G), newer G7 | NC A100 v4, NCads H100 v5, NCasT4_v3 (T4) | G2 (L4), G4 |
| Own silicon | Trainium (Trn2, Trn3), Inferentia (Inf2) | Maia chips run Microsoft's own services and are not rentable as VMs; AMD option: ND MI300X v5 | TPUs: v5e, v5p, v6e (Trillium), Ironwood (TPU7x) |
| Software for own silicon | AWS Neuron SDK, not CUDA | n/a | JAX and XLA, plus PyTorch support; check the TPU docs |

Some details worth knowing:

- **AWS P5** has up to 8 H100 GPUs with up to 3,200 Gbps of EFA networking and 900 GB/s NVSwitch between GPUs. **P6-B200** has 8 Blackwell GPUs and 1,440 GB of total GPU memory. The EC2 docs also list P6-B300 and P6e-GB200.
- **Azure ND H100 v5** is 8 H100 80 GB GPUs with 400 Gbps Quantum-2 InfiniBand per GPU, and there is no single-GPU size. ND is the large-scale training family, NC is for applied AI and inference, and NV is for visualization. Microsoft's NC A100 v4 page says it is deploying only net new capacity for the newer NCads H100 v5 (up to 2 H100 NVL 94 GB), so plan for A100 capacity not growing.
- **Google A3 Mega** (8 H100) gives up to 1,800 Gbps of network bandwidth between VMs when GPUDirect-TCPXO is set up. **A3 Ultra and A4** list up to 3,600 Gbps. Inside one VM the GPUs talk over NVLink at 900 GB/s (H100, H200) or 1,800 GB/s (B200).
- **Google Ironwood (TPU7x)** has 192 GiB of HBM per chip and pods of up to 9,216 chips. In November 2025 Google said it would be generally available "in the coming weeks". The eighth-generation TPU 8t (training) and 8i (inference) were announced in April 2026, with general availability promised "later this year". Check the TPU docs for what you can order today.

## Training versus inference

For **training**, you want many GPUs on a very fast network, in the same place: AWS P5 or P6, Azure ND, Google A3 or A4, or Trainium and TPUs if your software stack supports them. See [Training infrastructure](../training-infrastructure/).

For **inference**, you want enough memory for the weights plus KV cache, and the best bandwidth per unit of money. Small and medium models run well on one L4, A10G or L40S class card (AWS G-series, Azure NC, Google G2). Larger models need H100, H200 or newer, often several GPUs in one server. Inferentia and some TPU types target cost-efficient inference too, at the price of porting your serving stack.

## Quotas and reservations

This is where plans fail. Availability is a separate question from price.

- **Azure.** Every subscription starts with zero vCPU quota for GPU VM series in each region. You must request an increase for each series before you can create one, and approval is not instant. Having quota does not guarantee that capacity exists in the region.
- **Google Cloud.** A3 Ultra and A4 cannot be created as ordinary on-demand VMs. Google's consumption table allows Spot, Flex-start, or a future reservation (calendar mode or capacity block). A4X and A4X Max are available through capacity blocks only. GPU quota also applies per region, and other series such as A3 Mega and G2 can be created on demand. Check the current docs for each machine type.
- **AWS.** Large GPU instances are often obtained through **EC2 Capacity Blocks for ML**: you reserve a block of GPUs for a fixed period starting at a chosen date. P6-B200 launched this way. AWS also applies vCPU service quotas per instance family. Check the quota console for your family.

<Callout title="Ask early" kind="note">
Request quota and reservations before you need them, and in more than one region if you can. Waiting days or weeks for capacity is common for the newest GPUs.
</Callout>

<Deep title="Practical notes for platform teams">

Instance names do not tell you everything. Confirm the GPU variant (SXM or PCIe, memory size), the networking (EFA, InfiniBand, or plain Ethernet) and local storage on each instance's documentation page. For multi-node work, ask whether instances are placed close together, for example with placement groups on AWS, proximity placement on Azure, or compact placement policies on Google Cloud. The names of these features and their limits change, so verify in the docs. Mixing instance types in a single serving pool, with automatic fallback, helps with capacity shortages. SageMaker's Capacity-Aware Instance Pools (announced May 2026) do this on AWS for up to five instance types.

</Deep>

## What to take forward

- Match the family to the job: P, ND and A-series for training, G, NC and G2 for inference.
- Start from memory: weights plus KV cache decide the GPU, then bandwidth decides speed.
- Quota and capacity are the real gate. Request them first.
- Use reserved capacity for steady and guaranteed work, Spot for interruptible work with checkpoints.
