Kubernetes is the usual way to run many copies of a model server and keep them healthy. It was designed for small, fast-starting, CPU-bound web services, and LLM servers are the opposite: huge, slow to start and limited by GPU memory. Most of the useful knowledge is about where the defaults stop working. This lesson assumes you know [what a serving request does](../../serving/life-of-a-request/).

## GPU scheduling

Kubernetes does not see GPUs by itself. A **device plugin** (NVIDIA's is the common one, installed with the GPU operator or your cloud's GPU node image) advertises GPUs as a schedulable resource, such as `nvidia.com/gpu`. A pod asks for whole GPUs in its limits:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: llm-server
spec:
  tolerations:
    - key: nvidia.com/gpu
      operator: Exists
      effect: NoSchedule
  containers:
    - name: engine
      image: registry.example.com/llm-engine:1.0
      resources:
        limits:
          nvidia.com/gpu: 2   # whole GPUs; they cannot be fractionally requested by default
```

By default GPUs are whole units and are not shared between pods. Put GPU nodes in their own **node pool** with a **taint**, so ordinary pods do not occupy expensive nodes, and give the serving pods a matching toleration. Some clouds add such a taint automatically, so check yours. Sharing a GPU (time slicing, or MIG partitions on supported cards) exists, but see the failure modes lesson for the noisy-neighbour risk. The Kubernetes page on scheduling GPUs is the reference.

## Cold starts

A new replica must wait for all of these: a node to exist (minutes if the autoscaler must add one), the container image to download (a multi-GB image with CUDA libraries), the model weights to download and load into GPU memory (tens to hundreds of GB), and warm-up, such as capturing CUDA graphs. A cold start of several minutes is normal. Ways to shorten it:

- Keep the **image small** and separate from the **weights**. Do not bake 100 GB of weights into the image.
- **Cache** images and weights on the node (local NVMe or a shared cache) so a second pod on the same node starts faster.
- Use **safetensors**, which loads quickly and avoids the code-execution risk of pickled files.
- Keep **spare capacity**: a minimum replica count, or a warm pool of ready nodes.

## Autoscaling signals that work

The standard Kubernetes autoscaler scales on CPU. For LLM servers that is the wrong signal: the CPU is mostly idle even when the GPU is saturated. GPU utilisation is not much better, because it only says that some kernel was running, not how full the batch is. Use signals that reflect the engine's state:

| Signal | What it tells you | Note |
|---|---|---|
| Queue depth (requests waiting) | Demand exceeds capacity right now | Simple and responsive. A good primary signal. |
| Requests or tokens in flight | How much concurrent work each replica has | Scale to a tested target per replica. |
| KV cache utilisation | How close the replica is to running out of memory for new requests | Strong sign of saturation. Scale up well before 100 percent. |
| Time to first token (p95) | What users actually feel | Slower to react, good as a guard rail. |

Engines such as vLLM expose these as Prometheus metrics. Metric names change between versions, so read your version's metrics endpoint. Feed them to the autoscaler through the Prometheus adapter or KEDA, with a target found by load testing (see [capacity planning](../gpu-observability-and-capacity-planning/)). Scale up fast and scale down slowly, because a replica takes minutes to come back.

<Callout title="Cost" kind="cost">
Scale-to-zero saves money on idle GPUs, but the first request after idle waits for a full cold start, which can be minutes. It suits internal tools, batch jobs and development. For interactive products keep at least one warm replica, or accept the delay with a clear message to the user.
</Callout>

## Health checks and rollouts

Use a **startup probe** with a generous time limit, and make **readiness** true only after the model has loaded and a test generation works. A short liveness timeout will kill a pod that is simply still loading. Beware that a hung GPU can leave the HTTP server answering a trivial health endpoint, so add a probe that runs a tiny real generation, or watch GPU error metrics.

Rolling updates are hard when GPUs are scarce. The default surge creates a new pod before removing the old one, which needs spare GPUs you may not have. Set `maxUnavailable` and `maxSurge` deliberately, or roll one replica at a time. Give pods a long termination grace period and drain, so streams in progress finish instead of being cut.

<Deep title="Managed Kubernetes and managed inference on the three clouds">

EKS, AKS and GKE all run the Kubernetes control plane for you and offer GPU node pools with preinstalled drivers. Each has node autoscaling (for example Karpenter on EKS, or the cluster autoscaler and provider-specific provisioning on the others). Exact features and names change, so check the current docs. On AWS, SageMaker HyperPod Inference gives Kubernetes-native control on dedicated GPU clusters, including a two-tier KV cache and prefix-aware or KV-aware routing (per AWS's 2026 launch summary), while standard SageMaker endpoints are fully managed. Choose Kubernetes when you want one platform for many workloads and portable manifests. Choose a managed endpoint when you want fewer moving parts and can accept its limits. See [Bedrock, SageMaker, Foundry and Vertex compared](../../cloud/bedrock-sagemaker-foundry-vertex/).

</Deep>

<Disclosure client:visible title="Why not scale on GPU utilisation?">

GPU utilisation as reported by common tools is the share of time during which at least one kernel was running. A server handling one request at a time can show 90 percent, while a server batching 100 requests also shows 90 percent. It cannot tell you whether another request will fit.

</Disclosure>

## What to take forward

- Install the device plugin, taint the GPU pool, request whole GPUs.
- Expect cold starts of minutes. Separate weights from images and cache them.
- Scale on queue depth, in-flight work and KV cache use, not CPU.
- Make readiness mean "model loaded and generating", and roll out one replica at a time.
- Scale to zero only where a slow first request is acceptable.
