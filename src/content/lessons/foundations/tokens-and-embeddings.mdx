A language model never sees letters or words. Computers only work with numbers, so text is turned into numbers in two steps: first each piece of text becomes a whole number (an ID, like a page number in a dictionary), then each ID becomes a list of numbers that captures its meaning. Both steps explain things you will run into in practice: odd costs, odd failures, and how search over documents works.

## Tokens

A **tokenizer** splits text into pieces called tokens and gives each piece an ID number from a fixed list, the vocabulary. Common words get a single token. Rarer words are split into familiar parts, the way "unhappiness" can be read as "un", "happi" and "ness". Anything unusual falls back to smaller pieces, down to single characters. That keeps the vocabulary to a manageable size, typically tens of thousands of pieces, while still being able to write any text. (The most common way of building such a vocabulary is called byte-pair encoding, if you want to look it up.)

Three consequences follow.

- **Tokens are the unit of cost and capacity.** Prices are quoted per million tokens, and the context window is a token limit. For ordinary English, a token is roughly three quarters of a word, but that ratio is only a rule of thumb.
- **Not all text is equal.** Code, numbers, rare words and many non-English languages usually take more tokens per character than plain English, so the same content can cost more.
- **Models see pieces, not letters.** Questions such as counting the letters in a word are hard because the word may be one or two tokens. This is a tokenization effect, not a lack of intelligence.

## Embeddings

Each token ID is looked up in a table to get an **embedding**: a list of numbers, typically hundreds or thousands long. Think of it as coordinates. Two numbers would place a word on a flat map; a thousand numbers place it in a space with a thousand directions, which is impossible to picture but works the same way. During training the model adjusts these coordinates so that tokens used in similar ways end up near each other.

The same idea works on whole sentences and documents. A separate **embedding model** reads a piece of text and returns one vector for it. Texts with similar meaning land close together, which makes it possible to search by meaning rather than by keyword.

<EmbeddingSpace client:visible />

Closeness is usually measured by the angle between two embeddings (called **cosine similarity**: the smaller the angle, the more similar) or by plain distance. To search a library by meaning, you compute the embedding of every document once, compute the embedding of the question when it is asked, and return the documents closest to it. Many AI products work this way to answer from your own documents; it is called **retrieval**, and the RAG lessons build it step by step.

## Things worth remembering

- Embeddings from different models live in different spaces. You cannot compare a vector from one model with a vector from another, and changing the embedding model means re-embedding everything.
- Similar does not mean relevant. Two passages can be close in meaning and still not answer the question, which is why retrieval quality needs its own measurement.
- When documents are split into passages for search, the size of each passage matters, because one embedding has to summarise the whole passage.
