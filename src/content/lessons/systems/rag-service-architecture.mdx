The demo version of a RAG system is a script. The production version is a service with caching, access control, fallbacks, tracing and a way to update its knowledge. This lesson lays out one reference design and, more usefully, how each part breaks.

## Design choices that pay off

- **A fixed pipeline before an agent.** Retrieval, prompt and generation as a known sequence is easier to test and to cost. Add model-driven loops only where a fixed path fails.
- **Permissions at retrieval time.** Filter by the caller's access before ranking. Telling the model "do not reveal confidential files" is not access control.
- **One gateway for model calls.** It is the natural place for budgets, fallbacks and accounting, and it keeps provider details out of the rest of the code.
- **Trace everything, keep it queryable.** When someone reports a wrong answer, you should be able to open the trace and see what was retrieved, what was sent and what came back.
- **Evals in the loop.** Run the offline eval set on every change to prompts, chunking or models, and sample production traffic into it.

## Non-functional checklist

| Concern | Questions to answer |
|---|---|
| Latency | What is the budget for time to first token? Which steps can run in parallel? |
| Cost | Cost per question, and which component dominates? |
| Availability | What happens if the model, the index or the reranker is down? |
| Security | Who can see which documents? What do the logs contain? |
| Freshness | How soon after a document changes can it be found? |
| Quality | Which metric would tell you it got worse, and who is alerted? |

<Callout title="Start with the simple version">
Orchestrator, one index, one model and tracing are enough to launch. Add the cache, reranker, fallback and guardrails when the traces show you need them.
