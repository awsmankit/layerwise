The **context window** is the maximum number of tokens a model can consider in one request. Input and output both count against it. A larger window lets you send more, but it does not mean the model uses everything equally well, and it does not make sending more cheap.

## What fills the window

In a real application the user's message is usually the smallest part. The system prompt and rules, tool definitions, retrieved documents and the conversation history are resent on every request, and the reply needs room too. Pick a turn:

## Longer context has real costs

- **Money.** You pay for every input token on every request.
- **Latency.** Longer prompts take longer to process before the first token appears.
- **Quality.** Research on long contexts has found that models can use information in the middle of a long prompt less reliably than information at the start or end. Test with your own data rather than assuming a large window is fully usable.

## Prompt caching

If many requests begin with the same long prefix, such as a system prompt, a set of examples or a document, the platform can keep the processed form of that prefix and reuse it. Cached input tokens are typically billed at a discount and the first token arrives sooner. Details differ by provider: how a prefix is marked, how long it stays cached, whether writing to the cache costs extra, and the minimum prefix size. Check the current documentation for yours.

The rule that matters everywhere is **the cache matches from the start of the prompt**, so order decides what can be reused.

Put the stable parts first (instructions, rules, tool definitions, examples, reference documents) and the parts that change last (the conversation so far and the new message):

Look for cache read and cache write counts in the usage data that comes back with each response. A cache that is configured but never hit saves nothing and may cost extra to write.

## Keeping context under control

- **Summarise old turns** and keep recent ones verbatim.
- **Retrieve instead of stuffing.** Fetch the few passages that matter rather than sending the whole manual.
- **Trim tool output.** A tool that returns a huge JSON blob fills the window for every later step. Return only what the model needs.
- **Set a maximum output length** appropriate to the task.

<Disclosure client:visible title="Rule of thumb for deciding between caching and retrieval">

If the reference material is small enough to fit comfortably and is reused on most requests, caching it is simpler and often better. If it is large, changes often, or only a small part is relevant to each question, retrieve it.

</Disclosure>
