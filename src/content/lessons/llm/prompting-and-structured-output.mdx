A prompt is the whole input to the model, not just the question. Treating it as a small piece of software, with parts, tests and versions, is the difference between a demo and something you can run in production.

## The parts of a good prompt

<PromptLayers client:visible />

The model knows nothing about your situation unless you say so, so context carries constraints as well as facts. Use delimiters, such as XML-style tags or fenced blocks, to separate instructions from data: the prompt is easier to read, and text inside a document is less likely to be mistaken for an instruction.

## Getting output your code can use

Free text is hard to parse. There are three levels of control, from weakest to strongest. The middle one is the platform's structured output or tool-calling feature; prefer it when it is available.

<OutputLadder client:visible />

```python
from pydantic import BaseModel, ValidationError

class Ticket(BaseModel):
    category: str          # one of: billing, bug, question
    urgency: int           # 1 to 5
    summary: str

def extract_ticket(call_model, text, max_tries=3):
    prompt = f"Classify this message and reply with JSON only.\n<message>\n{text}\n</message>"
    for _ in range(max_tries):
        raw = call_model(prompt)
        try:
            return Ticket.model_validate_json(raw)
        except ValidationError as err:
            prompt += f"\nYour last reply was invalid: {err}. Reply with corrected JSON only."
    raise RuntimeError("Model did not return valid output")
```

<Callout title="Temperature zero is not a guarantee">
Setting temperature to zero makes output more repeatable, but not strictly identical. Differences in batching and hardware can still change a result, and a model update changes it for certain. Design for variation.
</Callout>

## Common failures and the usual fix

| Symptom | Likely cause | First thing to try |
|---|---|---|
| Ignores a rule | Rule buried in a long prompt | Move it near the end and state it once, clearly |
| Wrong format | Format described, not shown | Add an example of the exact output |
| Invents facts | Missing context, no permission to say "unknown" | Provide the facts and allow "I don't know" |
| Inconsistent labels | Vague categories | Define each category with an example |
| Follows instructions in a document | Data and instructions mixed | Delimit the data and say it is not instructions |

## Habits that pay off

- Keep prompts in files under version control, not inside code strings.
- Change one thing at a time and run your examples after each change.
- Save real failures as test cases. They become the start of an evaluation set, which is covered in the Evals track.
